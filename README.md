# flameflow-pd-shield

Обезличивание персональных данных для ботов Flameflow. В базу, на хостинг и в Claude API уходят только метки вида [PERSON_1], [PHONE_1]. Реальные значения живут в зашифрованном файле рядом с ботом и подставляются только в готовый ответ пользователю.

Состав: masker (находит ПД, ставит метки), vault (зашифрованная таблица метка-значение), restorer (возвращает значения в ответ, склоняет имена по падежным тегам от LLM), pd-scan (инвентаризация файлов).

## Подключение в существующий бот

Шаги проверены на боевом боте. Выполнять по порядку.

### 1. Установить пакет

В requirements.txt бота добавить строку:

```
flameflow-pd-shield @ git+https://github.com/Abubachirq/flameflow-pd-shield.git@v0.1.5
```

Всегда с тегом версии (@v0.1.5), не с голым main. Без тега строка в requirements не меняется при обновлении пакета, сборщик Railway берёт закешированную установку, и бот молча остаётся на старой версии — этот случай уже был (на боевом проекте, 02.08.2026). Обновление пакета в боте: новый тег в этой строке, коммит, пуш.

Локально: `pip install -r requirements.txt`. На Railway пакет поставится сам при деплое.

### 2. Сгенерировать ключ шифрования

Один раз выполнить:

```
python -m pd_shield.vault --new-key
```

Команда напечатает строку-ключ. Положить её в переменную окружения PD_SHIELD_KEY: локально в .env (файл уже в .gitignore), на Railway во вкладку Variables сервиса. Ключ больше нигде не хранить и никому не пересылать. Потеря ключа = потеря vault: реальные значения из меток восстановить будет нельзя, база переиндексируется заново.

### 3. Создать конфиг проекта

Файл pd_config.json в корне репозитория бота:

```json
{
  "names_env": "PD_NAMES",
  "enabled_types": ["person", "phone", "email", "birthdate", "address"],
  "vault_path": "/data/pd_vault.enc",
  "key_env": "PD_SHIELD_KEY"
}
```

- names_env: имя переменной окружения, откуда берётся словарь имён. Сам словарь — JSON-список имён в именительном падеже, задаётся рядом с ключом шифрования: локально в .env, на хостинге во вкладке переменных. Чем полнее список, тем надёжнее маскирование: словарь ловит то, что модель пропускает (редкие и несклоняемые фамилии).
- vault_path: на Railway путь на Volume (файловая система вне Volume не переживает редеплой). Локально можно `./data/pd_vault.enc`.
- Имена в файл конфига не кладутся: имя человека — это и есть персональные данные, а конфиг лежит в репозитории. В репозиторий уходят только настройки, имена и ключ — через переменные окружения.

### 4. Точка 1: обезличить данные до индексации

В пайплайне загрузки (обычно ingest.py), сразу после извлечения текста из документа и до нарезки на чанки:

```python
from pd_shield import Shield

shield = Shield.from_config_file("pd_config.json")

# внутри цикла по файлам, после extract_docx / extract_pdf / extract_xlsx:
text = shield.mask_for_index(text)
```

Для xlsx, где текст собирается по листам, маскируется текст каждого листа до make_xlsx_chunks.

### 5. Точка 2: обернуть вызов Claude API

Там, где бот вызывает Claude (обычно answerer.py), заменить:

```python
response = client.messages.create(model=..., system=..., messages=...)
```

на:

```python
response = shield.messages_create(client, model=..., system=..., messages=...)
```

Обёртка маскирует весь запрос (вопрос пользователя тоже), добавляет в system инструкцию про падежные теги, вызывает API и восстанавливает реальные значения в ответе. Больше в коде бота ничего не меняется.

### 6. Переиндексировать базу

Старый индекс собран из открытых текстов, поэтому после подключения:

1. Прогнать индексацию заново (python ingest.py): в новую базу попадут только метки.
2. Убедиться, что бот отвечает и имена в ответах на месте.
3. Старую chroma_db (или другую базу) с открытыми ПД удалить.

### 7. Проверить чек-листом

```
pd-scan data/chroma_db -o отчёт_пд.md --config pd_config.json
```

В отчёте по свежей базе не должно быть необезличенных находок, кроме помеченных «одно слово, проверить» ложных срабатываний — их проверить глазами. Это пункт 8 чек-листа перед сдачей.

## Как это работает, коротко

Masker находит ПД четырьмя способами: словарь имён из конфига (любые падежные формы), NER-модель natasha, регулярки на инициалы и падежные формы, регулярки на телефоны/email/даты рождения/адреса. Каждому значению vault выдаёт метку, одно значение всегда получает одну метку, включая разные написания одного человека: «Шумилина Вероника», «Шумилиной В.Н.» и «В. Н. Шумилиной» — это одна метка [PERSON_1].

Vault — json внутри шифра Fernet (симметричный шифр: один секретный ключ и запирает, и отпирает). Без ключа файл — случайные байты.

Restorer заменяет метки в ответе LLM реальными значениями. Падеж имени выбирает сама LLM тегом ([PERSON_1:дат] — «передайте документы Шумилиной Веронике»), склоняет локальная морфология. Метка без тега подставляется в именительном. Выдуманная метка превращается в «[неизвестно]» и пишется в лог.

## Ограничения

- Текст на картинках не распознаётся.
- Косвенные описания без имени («директор школы», «мама Пети из 2Б») не маскируются: это задача правил конфиденциальности в промпте бота, не этого пакета.
- Уже проиндексированные базы задним числом не чистятся — только переиндексация.
- Секреты (.env, ключи сервис-аккаунтов) — отдельная проверка, пакет ими не занимается.
